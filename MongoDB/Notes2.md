## Structured vs Semi-Structured vs Unstructured Data 

### Structured Data

- Structured data is highly organized data that follows a predefined schema and is stored in rows and columns. The structure of the data is known in advance and remains consistent across records. 

Example: Users Table 

| id | name  | email                                     |
| -- | ----- | ----------------------------------------- |
| 1  | Sonu  | [sonu@gmail.com](mailto:sonu@gmail.com)   |
| 2  | Rahul | [rahul@gmail.com](mailto:rahul@gmail.com) |

Every row follows: `id name email` - exactly. 

- Structured data follows a fixed schema where each record contains the same fields and data types. 

    This structure allows relational databases to efficiently store, query, and enforce constraints on the data. 

    Examples include customer records, banking transactions, inventory data, and employee information. 

### Semi-Structured Data 

- Semi-structured data does not follow a rigid tabular schema but still contains organizational markers such as keys, tags, or attributes that make the data partially structured. 

- Semi-structured data provides flexibility because records are not required to share identical structures. 

    However, the data still contains identifiable fields and attributes that allow applications to query and process it effectively. 

    JSON, BSON, XML and API responses are common examples of semi-structured data. 

- Document 1: 

```json
{
  "name": "Sonu",
  "email": "sonu@gmail.com"
}
```

Document 2: 

```json
{
  "name": "Rahul",
  "email": "rahul@gmail.com",
  "phone": "9999999999"
}
```

Both are valid. No fixed columns. But data still has structure: name, email, phone 

### Unstructured Data 

- Unstructured data is data that does not follow a predefinned schema and lacks an organized format suitable for direct storage in rows and columns. 

- Examples: Images, Videos, Audio Files, PDFs, Documents, Social Media Posts 

- Unstructured data does not fit naturally into relational tables because it lacks a predictable structure. 

    Such data often requires specialized storage and processing systems. 

    Examples include multimedia content, documents, emails, and free-form text generated by users. 

**Why Is MongoDB Considered Semi-Structured?**

MongoDB stores data in BSON documents that contain fields and values, providing a recognizable structure. 

    However, documents within the same collection are not required to follow an identical schema, making MongoDB a semi-structured database. 


## MongoDB 

MongoDB is a document-oriented NoSQL database that stores data in BSON documents instead of rows and columns. It is designed to provide schema flexibility, horizontal scalability, and high performance for modern applications. 

- Unlike relational databases where records are represented as rows, MongoDB stores records as documents. A document can contain simple values, nested objects, and arrays, making it possible to represent complex data structures naturally within a single record. 

**Why Was MongoDB Created?**

Traditional relational databases require predefined schemas and often rely on joins to represent relationships between entities. 

    As applications became larger and data structures evolved more rapidly, developers needed a more flexible approach to storing data. 

    MongoDB was created to address these challenges by allowing data to be stored as documents with flexible schemas while providing scalability and developer-friendly data modeling. 

**Collection vs Table** 

- Collection is a group of MongoDB documents and is conceptually similar to a table in a relational database. 

| SQL      | MongoDB    |
| -------- | ---------- |
| Database | Database   |
| Table    | Collection |
| Row      | Document   |
| Column   | Field      |

**What Is A Document?**

A document is the fundamental unit of data storage in MongoDB. Documents are stored in BSON format and consist of field-value pairs representing an entity's data. 

**BSON**

BSON (Binary JSON) is the internal data format used by MongoDB to store documents. 

    It extends JSON by supporting additional data types such as dates, binary data, and ObjectIds while providing efficient storage and retrieval. 

**ObjectId**

ObjectId is MongoDB's default unique identifier type used for the `_id` field of a document. It is automatically generated and ensures uniqueness across documents. 

- Every MongoDB document contains an `_id` field that uniquely identifies the document within a collection. By default, MongoDB generates an ObjectId consisting of information such as timestamp and random values, allowing documents to be uniquely indentified without requiring manually generated IDs. 

**Advantages of MongoDB**

- Flexible schema 
- Natural JSON-like document storage 
- Horizontal scalability 
- High write performance 
- Efficient handling of semi-structured data 

These characteristic of MongoDB make it well-suited for rapidly evolving applications and modern web development. 


## MongoDB Indexes 

- A MongoDB index is a specialized data structure that improves query performance by allowing MongoDB to locate documents efficiently without scanning an entire collection. 

- As collection grows in size, searching for documents by scanning every record becomes increasingly expensive. 

    MongoDB indexes improve performance by maintaining an optimized structure containing indexed field values and references to corresponding documents. 

    During query execution, MongoDB can use the index to quickly locate matching documents, significantly reducing query execution time and resource consumption. 

- Suppose collection: `users` contains: `100 Documents`

Finding a user by email is easy. Now imagine: `10 Million Documents`

Query: `db.users.find({email: "sonu@gmail.com"})`

Without an index, MongoDB must inspect documents one by one until it finds the matching record. This process is called: `Collection Scan`, equivalent to: `Full Table Scan` in SQL. 

    As data grows, this becomes slow. Indexes solve this problem. 

**How Is An Index Created?**

Syntax - Single field index: `db.users.createIndex({email: 1})` - The `1` means Ascending order. (Descending: -1)

**Does MongoDB Automatically Create Indexes?**

Yes. MongoDB automatically creates a unique index on the `_id` field for every collection. 

    This index ensures that documents can be efficiently located using their unique identifier. 

**Checking Existing Indexes:**

`db.users.getIndexes()`

**Removing Index**

`db.users.dropIndex("email_1")`

**Which Fields Should Be Indexed?**

Indexes should generally be created on fields that are frequently used in query filters, sorting operations, joins through lookups, and aggregation pipelines. 

    Proper indexing can significantly improve read performance, whereas excessive indexing can negatively impact write operations and storage utilization. 

- Common examples: email, phone, username, createdAt, userId 

**Drawbacks of Indexes**

Although indexes improve query performance, they consume additional storage space and increase the cost of insert, update, and delete operations because index structures must be maintained whenever data changes. 

- Every time a document is inserted, updated, or deleted, MongoDB must update both the document itself and all associated indexes. As the number of indexes increases, write operations become more expensive. Therefore, indexes should be created strategically based on actual query patterns rather than being applied indiscriminately. 

**MongoDB Index vs SQL Index**

The fundamental purpose is the same in both systems: improving query performance by avoiding full scans. 

    However, MongoDB indexes operate on document fields, whereas SQL indexes operate on table columns. 

    MongoDB additionally supports document-specific indexing strategies suited to flexible schemas. 


**How Would You Investigate A Slow MongoDB Query?**

I would first analyze the query pattern and verify whether appropriate indexes exist on the fields used for filtering, sorting, and aggregation. 

I would then use MongoDB'S explain plan to determine whether the query is performing a collection scan or utilizinng available indexes effectively. 

## Compound Index 

- A Compound Index is an index that includes multiple fields and is used to optimize queries that filter or sort using those fields together. 

- A Compound Index is an index built on multiple fields. It is used to optimize queries that frequently filter, sort, or search using the same combination of fields. 

Suppose query: 

```js
db.users.find({
    city: "Delhi",
    status: "active"
})
```

MongoDB can create: 

```js
db.users.createIndex({
    city: 1, 
    status: 1
})
```

This is called: `Compound Index`

- A compound index stores multiple fields within a single index structure rather than maintaining separate indexes for each field. This enables the database to efficiently process queries that involve multiple search conditions. 

    Compound indexes are particularly useful when applications frequently query data using the same set of fields together, as they reduce the amount of scanning and lookup work required during query execution. 

**Why Not Always Use Separate Indexes?**

Suppose query: 

```js
{
    city: "Delhi", 
    active: "active"
}
```

Separate indexes: 

`Index A -> city` `Index B -> status`

MongoDB may need to: Read both, combine results, find intersection. More work 

Compound index already stores: `city + status` together. Less work. 

### Leftmost Prefix Rule 

- Compound indexes follow the leftmost prefix principle, meaning queries are most efficient when they use the leading fields defined in the index. 

- Compound indexes follow the Leftmost prefix rule, meaning the database can efficiently utilize the index only when query conditions begin with the leading fields defined in the index. 

- The leftmost prefix rule exists because compound indexes are organized according to the order of their fields. The database can efficiently navigate the index only when queries begin with the leading indexed columns. 

    Queries that skip the initial fields may not fully benefit from the index because the database cannot directly locate the relevant portion of the index structure 

This is the MongoDB version of the SQL concept. Suppose: 

```js
db.users.createIndex({
    city: 1, 
    status: 1, 
    age: 1
})
```

MongoDB can efficiently use it for: 

```js
{
    city: "Delhi"
}
```

```js
{
    city: "Delhi",
    status: "active"
}
```

```js
{
    city: "Delhi",
    status: "active",
    age: 25
}
```

But: 

```js
{
    status: "active"
}
```

may not fully utilize the index. 

**Why Is Field Order Important In Compound Index?**

Field order determines how the index is organized internally. Since compound indexes follow the leftmost prefix rule, fields that are most commonly used in query filters should generally appear earlier in the index definition to maximize index utilization. 


## Aggregation Pipeline 

- Aggregation Pipeline is a MongoDB framework used to process and transform documents through a sequence of stages. It enables complex data analysis, filtering, grouping, sorting, calculations, and reporting operations. 

Need a way to: Filter, Group, Count, Calculate, Transform - data. 

    MongoDB created: Aggregation Pipeline. 

**Why Is It Called Pipeline?**

Think of a factory. Raw material enters. 

Stage 1: Filter data 

Stage 2: Group data 

Stage 3: Calculate totals 

Stage 4: Sort results 

    Final output comes out. Each stage receives the output of the previous stage. That's why it's called: Pipeline. 

- The Aggregation Pipeline processes documents through a sequence of stages, where each stage performs a specific operation and passes its output to the next stage. 

    This pipeline-based approach allows complex data transformations and analytical queries to be expressed in a clear and efficient manner. 

### Most Important Aggregation Stages 

- $match
- $group
- $project 
- $sort
- $limit
- $lookuup 

**$match**

- The `$match` stage filters documents according to specified conditions and passes only matching documents to subsequent stages. 

- Purpose - filtering. Equivalent to: `WHERE` in SQL. 

- Example - Only active users. 

- The `$match` stage is typically placed near the beginning of a pipeline to reduce the number of documents processed by later stages. This improves efficiency by eliminating unnecessary records early in the execution process. 

**$group**

- The `$group` stage groups documents based on a specified key and performs aggregated calculations such as `count`, `sum`, `average`, `minimum`, or `maximum` values. 

- The `$group` stage is used when analytical or reporting requirements involve combining multiple documents into summarized results. It enables operations such as calculating `totals`, `averages`, `counts`, and other aggregated metrics across groups of related records. 

- Equivalent to: `GROUP BY` in SQL. 

- Question: How much did each customer spend? 

    Need: Group by User, then: Calculate sum 

**$project**

- The `$project` stage reshapes documents by including, excluding, renaming or computing fields in the output.

    The $project stage is used to control the structure of documents returned by an aggregation pipeline. It can include, exclude, rename, or compute fields in the final output. 

- The `$project` stage is responsible for shaping the output of an aggregation pipeline. 

    It allows developers to select only the required fields, hide sensitive information, rename fields, or create computed values. 

    This improves efficiency by returning only relevant data to the client and reducing unnecessary payload size. 

- Select specific fields 

- Maybe document contains: `name email phone address salary`

    Frontend only needs: name, email. Use $project

**$sort**

- Equivalent to: `ORDER BY`

- The `$sort` stage orders documents according to one or more specified fields. 

    The $sort stage is used when results need to be returned in a particular order, such as newest records first, highest-priced products first, or users sorted alphabetically. Sorting improves usability and is commonly used in reporting, analytics, and user-facing applications.

**$limit**

- Equivalent to: `LIMIT` in SQL

- The `$limit` stage restricts the number of documents passed returned by an aggregation pipeline. 

    The $limit stage improves efficiency by reducing the size of result sets. It is commonly used in pagination, leaderboards, and recommendation systems where only a subset of records needs to be displayed. 

- Give me only N records 

**$lookup**

- MongoDB has no `joins`. How do we fetch related data? Answer: `$lookup`

- MongoDB's version of: `JOIN`

- The `$lookup` stage performs a left outer join between collections by matching related fields and combining documents from multiple collections. 

- Although MongoDB is a NoSQL database, applications often require related data from multiple collections. The `$lookup` stage enables MongoDB to combine data across collections in a manner similar to joins in relational databases. 

**What Is Aggregation Pipeline?**

Aggregation Pipeline is a framework used by MongoDB to process documents through multiple stages. Each stage performs a specific transformation such as filtering, grouping, sorting, projecting, or joining data, allowing complex analytical and reporting queries to be executed efficiently. 

**Why Use Aggregation Instead Of Find?**

The `find()` operation is primarily intended for document retrieval, whereas the `Aggregation Pipeline` supports advanced data transformation, grouping, calculations, analytics, and reporting requirements. 

**SQL Comparison**

| SQL      | MongoDB  |
| -------- | -------- |
| WHERE    | $match   |
| GROUP BY | $group   |
| SELECT   | $project |
| ORDER BY | $sort    |
| LIMIT    | $limit   |
| JOIN     | $lookup  |


**Have You Used Aggregation Pipeline?**

Yes. I have used MongoDB Aggregation Pipelines for filtering data, generating reports, performing grouping and counting operations, calculating metrics, implementing analytics features, and combining data from multiple collections using `$lookup`. 

- `match` -> Filters documents 

- `$group` -> Groups documents and performs calculations 

- `project` -> Selects or reshapes fields 

- `sort` -> Sorts documents 

- `$limit` -> Restricts result count 

- `$lookup` -> Combines data from multiple locations 


## Replication 

- Replication is the process of maintaining multiple copies of the same data across different database servers to improve availability, fault tolerance, and data redundancy. 

- Instead of: `Server A`, We have: `Server A`, `Server B`, `Server C` - All contain: same data 

    If one server fails, other servers continue working. Application remains available. 

**Why Was Replication Created?**

Imagine: One MongoDB Server. All data lives there. 

Question - What happens if that server crashes? 

    Result: Application down. Database unavailable. 

    Need: Backup copies - of the database. 

    This is why replication exists. 

## MongoDB Replica Set 

A Replica Set is a group of MongoDB servers that maintain the same dataset through replication. 

    It consists of one Primary node and one or more Secondary nodes. 

#### Primary Node

The Primary node receives all write operations and serves as the authoritative source of data. 

    Whenever the data changes, those changes are replicated to Secondary nodes. 

#### Secondary Node

Secondary nodes maintain copies of the Primary node's data by continuously replicating changes.

    They provide redundancy and can participate in failover if the Primary becomes unavailable. 

**Failover**

- Failover is the automatic process of promoting a Secondary node to Primary when the current Primary node becomes unavailable. 

- Failover ensures high availability by minimizing downtime during server failures. Because multiple copies of the data already exist, MongoDB can automatically elect a new Primary node and continue serving application requests with minimal disruption. 

- Suppose, Primary Server Crashes. 

    Question - Does application stop? No. 

    MongoDB automatically promotes one of the Secondary nodes to become the new Primary. 

    This process is called: Failover. 

**Understanding Primary and Secondary Node**

Imagine a classroom. Teacher writes notes on the background. Students copy those notes into their notebooks. 

    Teacher: Primary Server
    Students: Secondary Servers 

    Whenever teacher writes something new: Student immediately copy it. 

Similarly, whenever data is inserted, updated, or deleted in the Primary server, the same changes are copied to the Secondary servers. 

    This ensures that multiple copies of the database always exist. 

- Replication is a technique used to maintain multiple copies of the same database across different servers. 

    One server acts as the Primary node and receives all write operations, while the remaining servers act as Secondary nodes and continuously maintain synchronized copies of the data. 

    The primary purpose of replication is to improve availability, fault tolerance, and data redundancy. 

**Why Use Replication?**

Replication improves availability, fault tolerance, disaster recovery, and data redundancy. 

    It ensures that applications remain operational even when individual database servers fail. 

**Why Is Replication Important?**

Suppose an eCommerce application stores all its data on a single database server. It that server fails, the entire application may become unavailable. 

    Replication reduces this risk by maintaining additional copies of the database on other servers. As a result, even if one server becomes unavailable, the application can continue operating using another copy of the data. 

**What Happens If The Primary Server Goes Down?**

In a MongoDB Replica Set, if the Primary node becomes unavailable, the remaining Secondary nodes hold an election and automatically promote one node to become the new Primary. 

    This process is known as failover and helps maintain database availability. 


## Sharding 

- Sharding is a database scaling technique that distributes data across multiple servers by splitting the dataset into smaller partitions called shards. 

- Instead of: Server 1 -> All Data 

    We do: Server 1 -> Users A-F
           Server 2 -> Users G-M
           Server 3 -> Users N-Z 

    Now: Storage Load, Read Load, Write Load - is distributed across multiple machines. 

- As datasets grow beyond the capacity of a single server, database performance and storage limitations become significant challenges. 

    Sharding addresses this problem by dividing data into smaller subsets and distributing those subsets across multiple servers. 

    Each server stores only a portion of the total dataset, allowing the system to scale horizontally while improving storage capacity and throughput. 

**Why Was Sharding Created?**

Replication solves - Availability. But replication does not solve: Huge data size, Huge traffic. 

Suppose your MongoDB database contains: 10 Billion Documents. 

Even the most powerful server eventually hits limits: CPU, RAM, Storage

Question - Can we keep upgrading the server forever? 

    No. Eventually there is a limit. Need another solution. 

**Simple Understanding**

Suppose your school has: 10 students. One teacher can manage. 

Now suppose: 100,000 Students. One teacher cannot handle everyone. 

Solution - Divide students into classrooms. Class A. Class B. Class C. Class D - now workload is distributed. 

    This is exactly what Sharding does. 

## Replication vs Sharding 

**Replication**

- Purpose: High availability, Backup, Fault Tolerance. 

- Same data exists on multiple servers

**Sharding**

- Purpose: Scaling, Storage distribution, Traffic distribution 

- Different data exists on different servers. 

**Differnce between Replication and Sharding**

Replication creates multiple copies of the same data to improve availability and fault tolerance, whereas sharding distributes different portions of data across multiple servers to improve scalability and handler larger datasets. Replication focuses on reliability, while sharding focuses on scale. 


## Mongoose 

- Mongoose is an Object Data Modeling (ODM) library for MongoDB and Node.js that provides schema definitions, validation, middleware, relationships, and a structured way to interact with MongoDB collections. 

- Without Mongoose: You directly talk to MongoDB

- With Mongoose: Application -> Mongoose -> MongoDB 

- Mongoose provides: Schemas, Validation, Middleware, Population, Hooks, Model Methods 

    Think of it like: Express - makes Node.js easier. Similarly, Mongoose - makes MongoDB easier. 

- `MongoDB` itself is schema-flexible and does not enforce a strict document strucutre. `Mongoose` introduces schema definitions, validation rules, middleware capabilities, and abstraction layers that improve maintainability, consistency, and developer productivity. 

    It allows developers to model application data in a more structured and predictable manner. 

### Schema 

- A Schema in Mongoose defines the structure, validation rules, data types, and behaviour of documents stored within a collection. 

MongoDB allows: Document 1 -> `name, email` Document 2 -> `name phone linkedin` Document 3 -> `random fields`. 

    Possible. But applications often need consistency. 

Mongoose Schema says: Every user must have - `name email password`

### Schema Design

Schema design is the process of determining how application data should be modeled within MongoDB collections. 

    A well-designed schema balances performance, maintainability, flexibility, and query efficiency. 

    Decisions such as embedding versus referencing, indexing strategy, and document structure are important aspects of schema design.  

### Embedding vs Referencing

**Embedding**

- Store related data inside document 

    Example: User document contains addresses 

- Embedding is preferred when related data is frequently accessed together and does not grow without bound. It reduces the need for additional queries and improves read performance. 

**Referencing**

- Store related documents separately. 

    Example: Users collection. Orders Collection. Reference order owner using ID. 

- Referencing is preferred when relationships involve large datasets, independent updates, or one-to-many relationships that could result in excessively large documents. 


## Population 

- Population simplifies working with referenced relationships by automatically fetching and injecting related documents. 

    It provides functionality similar to joins in relational databases, allowing applications to retrieve associated data without manually performing multiple queries. 

- Suppose: Users Collection - `User A` Orders Collection: `order userId`. MongoDB stores: `userId` only. 

    Question - how do we get user details along with order? 

    Mongoose provides: populate()

**Is populate equivalent to SQL Join?**

    Population serves a similar purpose to joins by retrieving related data across collections. 

    However, it is implemented at the application layer by Mongoose rather than through native relational database join operations. 


## Middleware / Hooks in MongoDB 

- Middleware, also known as Hooks, are functions that execute automatically before or after specific Mongoose operations such as save, update, delete, or query execution. 

- Hooks allow developers to execute custom logic automatically during the lifecycle of database operations. 

    They help enforce business rules, perform validation, hash passwords, log activity, and implement cross-cutting concerns without duplicating logic throughout the application. 

- Suppose, everytime user registers - Need: `Hash Password` before saving. 

    Can write code everywhere. Messy. Need centralized mechanism. 

**Most Common Example**

Password Hashing. 

A common use case for Mongoose middleware is password hashing. A pre-save hook can automatically hash a user's password before it is stored in the database, ensuring consistent security practices across the application. 

**Pre Hook** 

Runs: Before Operation. 

Example - Before save, hash password. 

**Post Hook** 

Runs: After Operation

Example - After save, send notification. 

**Lean()**

- The `lean()` method instructs Mongoose to return plain JavaScript objects instead of full Mongoose documents, improving query performance and reducing memory usage. 

- Mongoose documents contain additional functionality such as change tracking, virtual properties, middleware support, and instance methods. 

    When only raw data is required, the lean() method bypasses document hydration and returns plain JavaScript objects. 

    This reduces overhead and improves performance, particularly for read-heavy operations. 

Normal query: `User.find()` returns - Mongoose document 

Mongoose document contains: Methods, Virtuals, Getters, Setters, Tracking - all of this consumes memory 

Suppose: 10000 Users. Need only data. No methods. No modifications. 

Use: `User.find().lean()`

**When Should You Use Lean?**

Lean should be used when data only needs to be read and no Mongoose-specific functionality such as document methods, virtuals, or change tracking is required. 

    It is particularly beneficial for high-performance read operations.
